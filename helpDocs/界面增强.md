# 界面增强（Fluent 风格组件代理）

本文记录一次「Fluent 风格界面增强」的移植：把一组 WinUI / Fluent Design 的观感特性
接到本项目现有的 Swing + FlatLaf 界面上。**没有引入新的 UI 框架，也没有改动任何 `.form` 设计器文件。**

| 项目 | 值 |
| --- | --- |
| 代码位置 | Fluent 增强：`src/com/wmp/downloader/tools/ui/fluent/`；SwingX 适配：`src/com/wmp/downloader/tools/ui/swingx/` |
| 开发工具 | `tools` |
| 安装入口 | `FluentUi.install()`（已接入 `UIStart.show()`）；忙碌标签另需 `LoadingBusyLabelUI.install()` |
| 自检脚本 | `run-ui-selftest.ps1`（根目录，主类名自动发现） |

## 一、装了哪七项

| 特性 | 实现 | 生效方式 |
| --- | --- | --- |
| **悬浮细滚动条** | `FluentScrollBarUI` | 全局 `UIManager["ScrollBarUI"]`，无需改代码 |
| **进度条扫动动画** | `FluentProgressBarUI` | 全局 `UIManager["ProgressBarUI"]`；**只改不确定态**，确定态仍由当前 LAF 绘制 |
| **WinUI 开关外观** | `FluentSwitchUI` + `FluentToggleSwitch` | 全局 `UIManager["CheckBoxUI"]`，21 个设计器复选框自动变开关 |
| **揭示高亮光晕** | `RevealEngine` + `RevealButtonUI` | 全局 `UIManager["ButtonUI"]`，所有按钮自动参与 |
| **语义色令牌** | `FluentColors` | 自绘组件从当前 Look & Feel 取色，自动跟随主题 |
| **忙碌标签加载动画** | `LoadingBusyLabelUI` + `LoadingBusyPainter` | 全局 `UIManager["BusyLabelUI"]`，`JXBusyLabel` 从旋转圆点变成滚动横杠 |
| **开发工具** | `StartupTrace` + `UiSelfTest` + `PngWriter` | 命令行运行 |

### 忙碌标签（`LoadingBusyLabelUI` / `LoadingBusyPainter`）

把「三根竖柱 + 中间柱内滚动横杠」的加载图标接进 SwingX 的 `JXBusyLabel`，
供 `Downloader` 的空白页居中等待动画使用。

SwingX 的 `BusyLabelUI` 契约<b>只有两个成员</b>，本适配器就只适配这两个，
其余参数一律用代码内默认值：

| 契约成员 | 本适配器的做法 |
| --- | --- |
| `BusyPainter getBusyPainter(Dimension dim)` | 返回 `LoadingBusyPainter`；`dim` 只用来做「图标太小就少画几根横杠」的降级 |
| `int getDelay()` | 按「周期 ÷ 帧数」换算：默认 `1600ms ÷ 20 = 80ms` |

<b>动画不需要自己开 Timer</b>：`JXBusyLabel` 自带一个按 `getDelay()` 驱动的 Timer，
每拍把 painter 的 `frame` 加一并重绘；项目里那段等待动画还额外用了一个 80ms 的手动泵帧。
所以 `LoadingBusyPainter` 只做「帧 → 相位」，两种驱动方式都兼容。
默认帧数取 20 正是为了与那个 80ms 泵帧对齐——`20 × 80ms = 1600ms` 一圈，
而标签自带 Timer 的 `getDelay()` 也正好是 80ms，速度一致。

墨色默认取<b>标签当前的前景色</b>，因此会跟随主题切换；
默认不绘制背景，不会在标签上盖一块底色。

#### 自然尺寸：别让加载窗里的图标缩成 26×26

加载窗 `PreloadDialog.form` 用的是「`new JXBusyLabel()` 且不设尺寸」的写法，
而 `JXBusyLabel.getBusyPainter()` 对这种标签是这样算尺寸的：

```java
Dimension prefSize = getPreferredSize();            // (0,0)
busyPainter = createBusyPainter(null);
if (!isPreferredSizeSet() && prefSize 为空) {
    Rectangle rt = busyPainter.getTrajectory().getBounds();
    Rectangle rp = busyPainter.getPointShape().getBounds();
    int max = Math.max(rp.width, rp.height);
    prefSize = new Dimension(rt.width + max, rt.height + max);
}
```

**它不看 `painter.getPreferredSize()`，只看轨迹形状与点形状的边界。**
而 `BusyPainter` 的默认构造函数把这两个形状按 26px 缩放，
于是加载窗里的图标只有 **26×26**——小到几乎看不清，窗口 `pack()` 也跟着缩窄。

修法是在 `LoadingBusyPainter` 构造时用 `init(...)` 声明自然尺寸：
轨迹设成 64×64、点形状设成**空**矩形，这样 `prefSize` 恰好是 64×64。
绘制本身不用这两个形状（`doPaint` 按传入宽高自行缩放），它们在这里纯粹是「尺寸声明」。
默认 64 与项目既有约定一致——`Downloader` 里那段等待动画显式设的就是 64×64。

#### 必须早于加载窗的构造

`Run.main` 的顺序是「先建加载窗，再 `UIStart.show()`」，而界面安装原本在 `show()` 里，
所以加载窗拿到的是**安装前**的状态，一次踩两个坑：

- 加载动画还是 SwingX 默认的**旋转圆点**（Swing 组件的 UI 在构造时就取定了，
  `JLabel` 的构造器会调用 `updateUI()`，之后装什么都来不及）；
- 窗口按 **Metal 外观** `pack()` 过一次（系统外观也是进 `show()` 才切的）。

因此 `common.UIStart` 上开了一个 `prepareUi()`：切换系统外观 + 安装界面增强，
由 `Run.main` 在 `PreLoadDialog.INSTANCE_CREATOR.create()` **之前**调用，
`show()` 内部再兜底调一次（幂等，不会重复记启动耗时）。
这样既满足「加载 UI 先于加载窗」，也没有绕开新架构——
`Run` 只用 common 层的 `UIStart` 接口，Swing 实现仍然只出现在 platform 层。

### 设计原则：优先「代理」，不新增控件类型

项目里 23 个面板中有 21 个是 **GUI Designer 的 `.form`**，
手改里面的控件类型会被设计器覆盖回去。
而 `ScrollBarUI` / `ProgressBarUI` / `CheckBoxUI` / `ButtonUI` 都是 Swing 的通用默认值——
替换它们，**所有既有控件立刻生效，且一个 `.form` 都不用碰**。

## 二、怎么开关

```java
FluentUi.install();                       // 装上全部（UIStart 已调用）
FluentUi.setRevealEnabled(false);         // 关掉光晕（低性能机器）
FluentUi.setSwitchStyleEnabled(false);    // 复选框恢复传统方块
FluentUi.setFluentScrollBarEnabled(false);
FluentUi.setFluentProgressBarEnabled(false);
FluentUi.refreshUI();                     // 切换单项开关后刷新已显示窗口
RevealEngine.setEnabled(false);           // 等价于 FluentUi.setRevealEnabled(false)
```

- **单个复选框**想保留传统外观：`cb.putClientProperty(FluentSwitchUI.DISABLE_KEY, Boolean.TRUE)`
- **形状**统一服从既有的「方角组件」设置（`is_use_square_component`），
  不会出现「按钮直角、进度条圆角」的自相矛盾。
- 启动时想看耗时：`StartupTrace` 默认开启，`-Dspeedbump.trace.startup=false` 可静默。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\run-ui-selftest.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\run-ui-selftest.ps1 -Dark
powershell -NoProfile -ExecutionPolicy Bypass -File .\run-ui-selftest.ps1 -Theme "Metal"
```

产物在 `out/ui-selftest/`：界面截图、组件树（含每个组件的实际尺寸）、UTF-8 报告。
退出码 0 = 全部断言通过。

它断言的是那些「不会抛异常、只会默默错掉」的东西：
开关是不是真的画成 40×20 轨道、传统复选框有没有被误改成开关、
表格 Boolean 列有没有被误改成开关、滚动条滑块是否可见、
光晕有没有真的提亮、**主题切换后这些 UI 代理是否还活着**，
以及**确定态进度条是否与当前 L&F 自身绘制逐像素一致**。

## 四、排查手册（都是实际踩过的）

### 1. 替换 UI 类必须自己写静态 `createUI`，否则会被父类悄悄顶替

`UIDefaults.getUI()` 是通过反射调用**静态方法** `createUI(JComponent)` 来创建 UI 实例的，
**不是**调用无参构造器。如果子类没定义它，就会「继承」父类的实现：

- `BasicScrollBarUI.createUI` → `new BasicScrollBarUI()`
- `BasicProgressBarUI.createUI` → `new BasicProgressBarUI()`
- `BasicCheckBoxUI.createUI` → `new BasicCheckBoxUI()`

于是 `UIManager` 里明明写着自定义类名，装上的却是普通控件，**而且不报任何错**。
本次四个 UI 代理与 `FluentToggleSwitch` 都必须显式定义 `createUI`。

### 2. 表格布尔列必须回退成传统复选框

`JTable` 会用 `JTable.BooleanRenderer extends JCheckBox implements TableCellRenderer`
（非 FlatLaf 主题下）当「图章」画布尔单元格。
如果不加区分地套用开关 UI，**所有勾选列都会变成开关**。

判定顺序（第一条才是最可靠的）：

1. `component instanceof TableCellRenderer / ListCellRenderer`（渲染器对象本身就是组件）；
2. 祖先链里出现 `CellRendererPane`；
3. `getParent() == null` 兜底。

> 曾经想当然地用「`getParent() == null` 说明是渲染器」。查 JDK 源码才发现是错的：
> `CellRendererPane.paintComponent` 里有 `if (c.getParent() != this) this.add(c);`，
> 渲染器在**绘制期间**的父容器正是那个 pane，并不为 null。

### 3. 自绘控件不能把文字交给 `BasicButtonUI.paintText`

`FluentSwitchUI` 最初调用 `BasicButtonUI.paintText` 画文字，于是出现两个问题：

- **禁用态文字变成黑色**。JDK 里那个方法的禁用分支是**老式浮雕画法**：
  先用 `background.brighter()` 在原位画一遍，再用 `background.darker()` 向左上偏移 1px 画第二遍。
  它**完全不读主题的禁用文字色**——FlatLaf 把控件背景设成深色，`darker()` 出来近乎纯黑，
  结果「禁用组件的文字反而显示为黑色」。
- **HTML 文本被当成普通字符串**。`BasicButtonUI` 在安装时会给 HTML 文本挂一个 `BasicHTML` 的
  `View`，真正的绘制由它完成；绕过 View 直接 `paintText`，界面上会显示出一串 `<html>…` 标签原文
  （项目里 `ParserCompatibilityDialog` 的复选框就是 HTML 文本）。

修法是把文字绘制收进 `FluentPainting.paintLabel`：自己按
`CheckBox.disabledText` / `Button.disabledText` 取禁用色，自己处理助记符下划线，
遇到 HTML 则交给 View（View 取的是组件前景色、它不区分禁用态，所以绘制期间临时替换前景色并在
`finally` 里还原）。

> 这一条是**用户报上来的**，不是自检发现的——原来的自检只覆盖了选中/未选中，
> 没有禁用态这一档。「可交互状态」至少要覆盖 常态 / 悬停 / 按下 / 禁用 四种，
> 少一种就等于把一类 bug 放进盲区。现已补上断言，并且**验证过它会失败**
> （注入「不灰化」后确实报错），否则一个从未失败过的回归测试没有意义。
### 4. `UIManager.put` 的 UI 类**不会**被主题切换抹掉（一条被实测推翻的猜测）

> 本节标题原本写的是「主题切换会重建整张 `UIManager` 默认值表」，并据此给 `FluentUi`
> 挂了一个「每次主题刷新重新灌入」的回调。**那个前提是错的**，用探针实测后更正如下。

`UIManager.put(key, value)` 写的是**用户默认值**，而 `UIManager.setLookAndFeel(...)`
会刻意**保留**用户默认值。实测（`FlatLightLaf` → `FlatDarkLaf` → 经 `ThemeChanger.easyChanger`
→ 直接切到 `Metal`）在每一步之后：

- `UIManager.getString("ScrollBarUI"/"ProgressBarUI"/"CheckBoxUI"/"ButtonUI")` 依然是我们写的类；
- **新建**的 `JScrollBar` / `JProgressBar` / `JCheckBox` / `JButton` 实际拿到的 UI 也都还是我们的实现。

所以「切一次主题就变回旧样式」并不会发生，`FluentUi` 里那个动态转换任务对「存活」并非必需。

**那它还有用吗？有，但理由不同**：`ButtonUI` 的安装是**有条件的**
（`RevealButtonUI` 继承自 `FlatButtonUI`，只在 FlatLaf 家族下才装）。
换成 Metal / Windows Classic 这类外观时，需要**重新评估这个条件**并把它撤掉——
这才是那个回调真正在起作用的地方，而不是「重新灌入」。
（实测：不撤掉也不会抛异常，但外观不受保证。）

另一条仍然成立：关闭某项时**不能**简单 `UIManager.remove(key)`，
那会把 Look & Feel 自己的实现一起删掉，`getUI` 返回 null，`setUI(null)` 让控件崩掉。
正确做法是从 `getLookAndFeelDefaults()` 取回 L&F 原始值写回去。

> 教训：这类「框架会怎么处理我的设置」的问题，**读源码 + 写探针实测**比推理可靠得多。
> 我当初是「推理」出这个坑并写进文档的，结果它并不存在；
> 而真正的风险点（条件性安装需要重评估）反而被这个错误前提盖住了。

### 5. 主题给的滚动条滑块色可能和背景一模一样

本项目的滚动条是「悬浮细条」——**不画轨道**，滑块直接叠在面板底色上。
而 `FluentColors.scrollThumb()` 原本直接取 `ScrollBar.thumb`，
结果在 **Windows Classic** 外观下该键的值与 `Panel.background` **完全相同**：
用底色画在底色上，alpha 混合后毫无变化，**滚动条在界面上彻底消失**
（自检里表现为「滑块像素 0 / 1972，最大对比度 0」）。

现在 `FluentColors.ensureVisible()` 会先做一次对比度校验：
候选色与滚动条所在背景的最大通道差不足 24，就改用与文字同源的次要色。
修复后同一主题下的对比度是 96。

> 这次排查的教训：一开始只在 FlatLaf 主题下看，一切正常；
> 把自检扩到 Metal / Windows Classic 之后才暴露。
> **「只在一个主题下验证」约等于没有验证**——不同 L&F 之间的取值差异，
> 只有换外观各跑一遍才会现形。
### 6. 进度条只接管不确定态（装饰器）

`FluentProgressBarUI` 的职责是**分裂**的：

| 状态 | 由谁绘制 |
| --- | --- |
| `isIndeterminate() == true` | 本类：一条高亮带单向扫过 |
| 确定进度（含文本、方向、边框、内边距、圆角、尺寸） | **当前 Look & Feel 自己的 `ProgressBarUI`** |

也就是说确定态的外观完全跟随主题：FlatLaf 的 Mac Light/Dark、Darcula、IntelliJ，
以及 Metal / System 等外观下都保持它们原本的样式，本类不去「重新发明」一个进度条。
被替换掉的只有原来那个「方块来回弹跳」的不确定态。

实现上有三个必须注意的点：

- **必须继承 `ProgressBarUI`**（而不是 `BasicProgressBarUI`），
  因为 `JProgressBar.updateUI()` 里有 `setUI((ProgressBarUI) UIManager.getUI(this))` 的强制类型转换。
- **取 L&F 自己的 UI 要用 `UIManager.getLookAndFeelDefaults().getUI(c)`**，
  不要自己反射 `createUI`。前者是 JDK 内部机制，能实例化
  `com.sun.java.swing.plaf.windows.*` 这类**未导出包**里的实现；自己反射会因模块封装失败。
- **要防共享单例**：部分 L&F（尤其 Windows 系）的 `createUI` 返回单例，
  对它调 `installUI` 会把内部状态指向新组件，正在用它的其它进度条会跟着画错。
  本类用「连续取两次是否为同一对象」识别，命中时改用 `BasicProgressBarUI` 兜底。

自检对此的验证是**逐像素对照**：拿同一个组件装一份 L&F 原生 UI 当参照，两边画出来必须完全相同
（当前结果：差异 0 / 3360 像素）。这比「断言某个颜色」更硬——
后者默认「我知道 L&F 该画成什么颜色」，而这条需求恰恰是「不由我决定」。

> 另外，任务卡里的进度条高度由 `UITools.createProgressBarPanel` 从 12px 改成了 6px，
> 这是**布局**上的独立改动（与谁绘制无关）。若想恢复原高度，改那一行的 `barHeight` 即可。

### 7. 光晕必须画在「背景之上、内容之下」

FlatLaf 的绘制顺序是
`update() → [paintBackground] → paint()（图标 + 文字）`。
所以 `RevealButtonUI` 覆写 `paint`，在 `super.paint` **之前**画光晕。

> 一开始覆写的是 `paintBackground`，结果 `setContentAreaFilled(false)` 的按钮
> （恰恰是最需要悬停反馈的那一类）完全没有光晕——因为那个方法根本不会被调用。

### 8. 光晕只在 FlatLaf 外观下安装

`RevealButtonUI` 继承自 `FlatButtonUI`，换成 System / Metal / Windows Classic 后
它读不到 FlatLaf 的默认值。`FluentUi.applyUiDefaults()` 会判断外观类型，
宁可这类主题下没有光晕，也不能让按钮坏掉。

### 9. 开关比复选框宽约 20px

轨道 40px vs 方框 20px。GridBagLayout 会自动吸收，但**固定尺寸或紧凑布局**里
可能出现轻微位移，必要时给该控件设 `FluentSwitchUI.DISABLE_KEY` 保持原样。

### 10. 本项目 classpath 缺少 `imageio-core`

`.idea/libraries/imageio_plugins_3_13_1.xml` 引用了十二猴子的格式插件
（bmp / tiff / webp …），却没有引用它们共同依赖的 `imageio-core`。
`ImageIO` 首次使用会扫描 SPI，插件类加载不到父类就抛
`ClassNotFoundException: com.twelvemonkeys.imageio.spi.ImageReaderSpiBase`——
**任何 ImageIO 调用都会失败**。主项目自己不用 ImageIO 所以一直没暴露。

自检因此自带 `PngWriter`（用 `Deflater` 手写 PNG），不依赖 ImageIO。
若要修 classpath，把 `imageio-core` 与 `common-*` 补进该库即可。

### 11. `DataControl` 静态初始化里的地雷（已修）

`load()` 里 `configureLogPath` 失败时会调 `ToastMessage.show(Downloader.mainFrame, ...)`，
而静态初始化阶段主窗口必然为 null，Toast 库抛 `IllegalArgumentException`，
异常从静态块冒出去 → **`DataControl` 类永久不可用**（后续全是 `NoClassDefFoundError`）。
现已改为「先记日志，只有窗口已存在时才提示」。

### 12. 脚本与命令行环境的三个小坑

- `.ps1` 必须是 **UTF-8 with BOM**：Windows PowerShell 5.1 对无 BOM 文件按 ANSI 解码，
  中文注释会变成乱码并引发语法错误。
- `Get-Content out-cp.txt -Raw` 的结尾换行会污染 classpath 的**最后一个**条目
  （表现为「jar 明明存在却报找不到包」），必须 `.Trim()`。
- 原生命令往 stderr 写日志时，若 `$ErrorActionPreference='Stop'` 且 stderr 被合并，
  脚本会以失败状态收场——即使自检本身通过。调用处需临时放宽。

### 13. `new JDialog()` 拿不到主题刷新（owner 是共享隐藏窗）

`ThemeChanger` 刷新外观时遍历的是 `JWindow.getOwnerlessWindows()`。
而 `new JDialog()` 会被 Swing 自动挂到 `SwingUtilities$SharedOwnerFrame` 这个共享隐藏窗上——
`getOwner()` 非 null，于是它**根本不在「无主窗口」列表里**，`UIManager` 换了、这扇窗纹丝不动。
表现为「点了深色/强调色，配置变了、界面没变」，日志里只有一行 `窗口刷新失败`（其实也没失败，是被跳过了）。

欢迎页（`platform.ui.swing.window.WelcomePage`）是第一个长期存在、又要即时预览主题的对话框，
所以这个问题第一次暴露出来。它的做法是把 `SwingUtilities.updateComponentTreeUI(this)`
注册成 `ThemeChanger` 的动态转换任务——这样刷新时机正好落在
`FlatAnimatedLafChange.hideSnapshotWithAnimation()` 之前，与主题切换动画同拍；
窗口销毁时记得 `removeDynamicConverter` 摘掉。

两个连带坑：

- `updateUI` 会顺带调整控件状态并可能补发 `ItemEvent`/`ActionEvent`。监听器分不清
  「用户点的」还是「刷新捎带的」，一律写进配置的话，光是换一次主题就可能把控件当时的状态盖到配置上。
  重建期间要用一个 `rebuilding` 标志把监听器挡住。
- 字号是全局 `defaultFont`，改了以后整窗首选尺寸也会变。窗口不可缩放时，
  必须 `pack()` 才能跟上内容（尺寸没变时它是空操作）。

### 14. `MultiplePanel.createPanel()` 在构造器里跑，早于子类字段初始化

`common.ui.components.MultiplePanel` 是「一份声明、多份平台实现」的容器：子类在
`createPanel()` 里把当前平台的面板 `putPanel(...)` 进去，使用方只调 `getPanel()`。
它把 `createPanel()` 放在**构造器**里调用，于是：

```java
private final JPanel panel = new JPanel();   // ← 这行在 createPanel() 之后才执行
@Override protected void createPanel() {
    putPanel(panel);                          // ← 拿到的是 null
}
```

`putPanel` 因此会拒绝 `null` 并抛出带说明的异常——把「静默拿到 null、后面某处才 NPE」
变成当场报错。写子类时字段一律不写初始化器，全部在 `createPanel()` 里赋值。

欢迎页的页面还多一步 `bind(host)`：`createPanel()` 只搭控件（那时外壳还不存在），
填初值和挂监听放到 `bind()`，避免构造期就去碰还没准备好的对象。

## 五、自检自身的两个陷阱

自检是用来「发现别人 bug」的，它自己的判据写错时同样会静默骗人。
下面两条都是**先在 Windows Classic 上暴露、再回头修判据**的真实记录。

### 1. 比像素必须把 alpha 算进去

`countDifferentPixels` 最初只比 RGB（`colorDistance` 用的是 getRed/getGreen/getBlue）。
而自绘控件的「槽位」是**透明**像素，透明像素的 RGB 也是 0——
于是「墨色恰好是纯黑」的外观下，槽位移动被判成「画面毫无变化」，动画断言**假绿**。

Windows Classic 的墨色就是纯黑，于是加载动画明明在动，断言却说「画面不随 frame 变化」；
Mac Light 之所以一直能过，只是因为它的墨色 #262626 与 0 差 38，**属于运气**。
判据已改为「任一 RGB 通道相差 > 2 **或 alpha 不同**」。

### 2. 判颜色不能认纯色

HTML 文本的着色断言最初写成「存在与 `#C42B1C` 相差 ≤ 40 的像素」。
在 FlatLaf 外观下过得好好的，到 Windows Classic 就变成 0 个——因为
**文字是否走 LCD 次像素抗锯齿由外观与桌面设置决定**（FlatLaf 会显式关掉，Windows 系外观不关）。
一旦走 LCD，红字实际是 `#E3B8B4`、`#D78078` 这类被冲淡的浅红，离纯色差 150 开外：

```
文字区颜色直方图： #F0F0F0×7970  #E3B8B4×33  #ACACAC×15  #595959×6  #D78078×6
```

改成量**文字的横向范围**后判据稳固得多：HTML 生效时画的是「加粗与着色」5 个字（实测 40–41px），
若把标签原文当普通字符串画则是 50+ 字符（实测 255–256px，被可用宽度截断）——**相差 6 倍**，
而且完全不受抗锯齿方式影响。副判据「红色分量明显压过绿蓝」的阈值也随之放宽到 25。

### 3. 别用 `-SkipCompile` 跑在负向注入过的产物上

做负向测试时改了源码、脚本自动编译、断言如期失败；随后**只还原源码却用 `-SkipCompile` 再跑**，
于是跑的还是那份注入过的 `.class`，三个主题一起「失败」，白白排查了一轮。
负向测试之后一定要重新编译（去掉 `-SkipCompile`）。
