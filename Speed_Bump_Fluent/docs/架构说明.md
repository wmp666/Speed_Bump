# 架构说明

本文记录 `Speed_Bump_Fluent` 的层次划分、令牌体系，以及若干「看起来可以更简单、但实际不能」的设计决定。
**改动组件之前请先读第五节（坑与约束）**，那里每一条都对应一个真实踩过的 bug。

---

## 一、分层与依赖方向

```
        page/          任务 · 创建任务 · 设置          ← 只关心「有哪些内容」
          │
         ui/           FluentWindow · FluentTitleBar
          │            FluentNavigationView · FluentPage   ← 只关心「框架怎么搭」
          │
     component/        Button · ToggleSwitch · CheckBox · RadioButton
          │            TextBox · TextArea · ComboBox · Card
          │            ProgressBar · ScrollPane             ← 只关心「单个控件怎么画」
          │
       theme/          FluentColors · FluentTypography
          │            FluentMetrics · FluentIcons
          │            FluentPainting · FluentTheme          ← 令牌与工具，不依赖任何上层
          │
      backdrop/        NativeBackdrop · BackdropMaterial     ← 只碰 Win32，不认识界面
       reveal/         RevealEngine                          ← 只碰鼠标与绘制，不认识控件类型
```

**规则只有一条：箭头不许反向。** 令牌层不认识「按钮」，材质层不认识「窗口内容」。
好处很直接：换主题、换材质、换配色，都只需要动 `theme` 与 `backdrop`。

`theme → backdrop` 是唯一的横向依赖（主题切换时要告诉 DWM 用深色标题栏），
而且是通过 `NativeBackdrop.setDarkThemeSupplier(FluentTheme::isDark)` **注入**的，
避免两个包静态初始化时互相拉死。

## 二、为什么要用 FlatLaf 打底

自研组件库覆盖了「高频核心控件」，但 Swing 还有一大批冷门组件：
`JComboBox` 的下拉弹窗、`JPopupMenu`、`JFileChooser`、`JTextArea` 的输入法、
`JTable`、`JToolTip`、剪贴板渲染……**为每一个都重写 UI 代理是不划算的**。

因此策略是：

- **底座**：FlatLaf 提供这些组件的渲染，`FluentTheme.publishDefaults()` 把 Fluent 令牌
  灌进 `UIManager`（强调色、圆角、滚动条、弹窗背景等），让它们也「大致是 Fluent 的样子」；
- **上层**：`component` 包里的自绘组件**完全不依赖 FlatLaf**，只读 `FluentColors` 等令牌。

这样既保住了视觉一致性，又不至于把 Swing 重造一遍。

> 反例说明为什么自绘组件不能依赖 L&F：
> `FlatComboBoxUI` 会**无条件**绘制自己的圆角背景
> （源码 `if (paintBackground || c.isOpaque())`，`paintBackground` 默认 `true`），
> 于是 `FluentComboBox` 只能顺着它、而不是跟它抢绘制权——这也是这个组件几乎不改绘制的原因。

## 三、颜色令牌

`FluentColors` 用**语义命名**（对齐 WinUI 3 的 brush 命名），而不是 `gray200` 这类色阶命名。
语义命名的好处是深色主题不需要重新理解整套色阶，只需要换一张表。

| 令牌 | 用途 | 浅色 | 深色 |
|:--|:--|:--|:--|
| `layer()` | 窗口最底层材质着色 | 白 70% | #202020 70% |
| `card()` | 卡片填充 | 白 80% | 白 5% |
| `cardStroke()` | 卡片描边 | 黑 8% | 白 7% |
| `control()` / `controlHover()` / `controlPressed()` | 控件三态填充 | 白 70/84/55% | 白 6/10/4% |
| `stroke()` / `divider()` | 描边 / 分隔线 | 黑 6/8% | 白 7/8% |
| `text()` / `textSecondary()` / `textDisabled()` | 三级文字 | 黑 89/61/35% | 白 100/78/35% |
| `accent()` / `accentHover()` / `accentPressed()` | 强调色三态 | #0078D4 | #60CDFF |
| `onAccent()` | 强调色之上的文字 | 白 | 黑 |
| `accentSubtle()` | 强调色淡化底（选中态、进度条轨道） | 强调色 13% | 强调色 20% |
| `solidCard()` / `flyout()` | 不透明卡面（弹窗、Tooltip） | 白 | #2C2C2C |

### 两个反直觉的地方

**1）Fluent 的材质层是半透明的，这是功能不是装饰。**
不用半透明，底层 Mica/Acrylic 就完全透不出来。所以令牌里大量颜色带 alpha，
绘制时直接 `setColor` 即可（Swing 默认就是 SrcOver 合成）。

**2）「无材质回退」不能把每个半透明令牌各自与底色合成。**
卡片是画在材质层**之上**的，如果卡片和材质层都与同一底色合成，两者算出来会**完全相同**——
界面上表现为「卡片和背景一样白，只剩一圈描边」。
所以 `FluentColors.resolve(color, aboveLayer)` 显式区分「材质层本身」与「叠在材质层之上的表面」，
合成顺序必须与真实绘制顺序一致。

## 四、尺寸与字体令牌

`FluentMetrics` 的数值对齐 Fluent 2 规范：控件高 32、圆角 4/8/12、
导航项高 36、导航选中指示条 3×16、滚动条 12、页面内容最大宽度 1080。

`FluentTypography` 的字号阶梯是 12 / 14 / 18 / 20 / 28 / 40 / 68（整数点值）。
字体族三级降级：`Segoe UI Variable Display`（Win11）→ `Segoe UI`（Win10）→ 逻辑字体（其它系统）。
中文等 CJK 字形由 Java 的字体回退链自动处理，**不要**显式指定「微软雅黑」。

## 五、坑与约束（改代码前必读）

### 1. Mica 在 layered 窗口上「假成功」

- `DwmSetWindowAttribute(SYSTEMBACKDROP_TYPE)` 在 Win11 上对 Swing 的透明窗口**返回成功但不渲染**；
- 于是「失败就回退」的逻辑永远不触发 → 用户看到「开了 Mica 没效果」。

**约束**：`NativeBackdrop.forceBlurInsteadOfMica` 保持 `true`。除非窗口不再是 layered 的，
否则不要关掉它。

### 2. 材质必须延迟重试

窗口句柄靠 `EnumWindows + IsWindowVisible` 按进程 PID 枚举，`setVisible(true)` 刚返回时
窗口尚未进入可见状态 → 句柄为 0 → 被误判为「不支持材质」→ **永久**退化为不透明。

**约束**：`FluentWindow.applyBackdrop()` 的「乐观 + 轮询重试」结构不要简化掉。

### 3. 无边框窗口的缩放只能靠全局鼠标监听

鼠标事件由**最深的子组件**接收，边缘区域通常被内容组件盖住，
挂在窗口上的 `MouseMotionListener` 根本收不到事件。

**约束**：`FluentWindow.handleGlobalMouse` 是必要的；同时 `FluentTitleBar` 的拖动逻辑
必须先问 `window.isOnResizeEdge(...)`，否则「在顶部边缘按下」会同时触发缩放和拖动。

### 4. 不要自己给窗口画圆角

原生模糊作用在**整个窗口矩形**上。若应用把四角画成透明，露出的仍是方角模糊层，
得到「圆角外壳 + 方角模糊」，比直角更难看。

**约束**：圆角交给 DWM 的 `DWMWA_WINDOW_CORNER_PREFERENCE`（Win11 生效）。
Windows 10 上就是直角——这与 Windows 10 上其它 Fluent 应用一致。

### 5. 文本框用「外壳 + 内层」结构

`FlatTextFieldUI.paintBackground` 的判定是
`if (!c.isOpaque() && getOutsideFlatBorder(c)==null && hasOpaqueBeenExplicitlySet(c)) return;`，
也就是说内层必须**显式** `setOpaque(false)` 才能拿到完全透明的输入区。
外层负责圆角底与 2px 焦点底线，内层负责文本、光标、选区、输入法、剪切板——最不该重造的部分。

**约束**：内层额外 `setBackground(new Color(0,0,0,0))` 做双保险，
避免任何版本的 L&F 再画一层底把半透明叠成两层加深。

### 6. 主题切换必须在 EDT 上同步执行

`FluentTheme.refresh()` 在非 EDT 调用时会 `invokeLater` 后立即返回。
如果调用方（例如自检）在主线程接着布局和绘制，就会与 EDT 上的主题刷新竞争，
表现为「某些主题色元素凭空消失」。

**约束**：任何「改主题 → 立刻截图/测量」的代码都必须整体放进 `invokeAndWait`。

### 7. 脚本必须带 UTF-8 BOM

Windows PowerShell 5.1 对无 BOM 的 `.ps1` 按 ANSI 解码，中文注释会变成乱码并引发语法错误。

### 8. 别用子进程读注册表，也别「先 waitFor 再读管道」

`ProcessBuilder` 的两个独立陷阱叠在一起：

- **性能**：`reg query` 子进程实测一次 11.7 秒。它服务于「跟随系统主题」，
  而该功能在 EDT 上同步执行 → 界面冻结十几秒。
  已改为 FFM 直读 `RegGetValueW`（`WindowsRegistry`），<1ms。
- **正确性**：`waitFor(超时)` 然后才读 stdout 是经典死锁模式——
  子进程输出填满管道缓冲区时会阻塞在写、永不退出，于是只能靠超时兜底，
  而超时值本身又是拍脑袋定的。正确做法是读到 EOF，`waitFor` 只作最后的短兜底。

### 9. 主题监听器：强引用泄漏，弱引用失效

`addListener(this::repaint)` 把回调塞进强引用列表 → 组件销毁后不释放；
改成弱引用回调 → `this::repaint` 每次都是新对象，除列表外无人强引用它，**静默失效**。

**解法**：把**组件本身**作为弱键放进 `WeakHashMap`，值用共享常量
`Boolean.TRUE`（值不反向引用键，条目才能在组件回收后过期）。
组件实现 `FluentTheme.ThemeAware`，`refresh()` 遍历一份键快照并回调。

### 10. 页面应当延迟构建

三个页面在启动时全部构造接近 2 秒，而用户启动后只看得到第一个页面。
`FluentNavigationView.addPage(title, glyph, Supplier<JComponent>)` 支持延迟构建，
首次被选中时才调用工厂。副作用是自检必须主动遍历所有页面 ——
这反而是好事：某个页面构造失败会立刻暴露在 `--selftest` 报告里，而不是等用户点开才崩。

### 8. 卡片在 BoxLayout 里要锁住最大高度

`JPanel` 用 `BorderLayout` 时 `getMaximumSize()` 是 `Integer.MAX_VALUE`，
放进纵向 `BoxLayout` 会被拉伸填满剩余空间。

**约束**：`FluentCard` 覆写 `getMaximumSize()` 把高度锁为首选高度；
`FluentPage.CenteringPanel` 也只给子组件首选高度，不做纵向拉伸。

## 六、如何扩展

### 新增一个页面

```java
public class FooPage extends FluentPage {
    public FooPage() {
        super("标题", "副标题");        // 标题区固定，内容列自动居中且限宽 1080
        FluentCard card = new FluentCard("分组标题", "分组说明");
        card.addRow("设置项", "说明文字", new FluentToggleSwitch("启用", true));
        add(card);
        gap(FluentMetrics.SPACING_L);
    }
}
```

注册：

```java
navigation.addPage("标题", FluentIcons.PAGE, new FooPage());
```

### 新增一个自绘控件

```java
public class FluentFoo extends JComponent {
    public FluentFoo() {
        FluentTheme.addListener(this::repaint);   // 主题切换自动重画
        // 需要光晕才注册：RevealEngine.register(this);
    }

    @Override protected void paintComponent(Graphics g) {
        Graphics2D g2 = (Graphics2D) g.create();
        try {
            FluentPainting.antialias(g2);
            Shape shape = FluentPainting.roundRect(this, 0, FluentMetrics.RADIUS_SMALL);
            FluentPainting.fill(g2, shape, FluentColors.control());
            RevealEngine.paint(this, g2, shape);   // 背景之上、内容之下
            // …绘制内容…
            if (isFocusOwner()) FluentPainting.focusRing(g2, this, FluentMetrics.RADIUS_SMALL);
        } finally {
            g2.dispose();
        }
    }
}
```

三条约定：**从 `FluentColors` 取色**、**用 `FluentPainting` 画**、**注册主题监听**。

### 新增一种材质

1. 在 `BackdropMaterial` 里加枚举值（补上 DWM 的 `SYSTEMBACKDROP_TYPE` 与 accent state）；
2. 在 `NativeBackdrop.resolve()` 里补降级规则；
3. 在 `SettingsPage` 的下拉框里加上选项。

## 七、自检机制

`--selftest` 走的是 `FluentApp.buildWindow()`——**与真实启动完全同一套装配代码**。
测试若自己另搭一棵组件树，就失去了「测的就是真实界面」的意义。

流程：`buildWindow()` → `pack()` + `setSize()` + `validate()` → 递归 `doLayout()`
→ 明暗两轮：`setMode()` → 重布局 → 离屏 `paint()` 到 `ARGB` 图像 → 四类校验 → 写报告。

之所以要 `pack()`，是为了让窗口先创建一次不可见 peer，组件树才是 displayable、
布局才会真正发生；否则所有组件尺寸都是 0。

校验阈值只用来判断「有没有东西」，不追求精确的视觉回归——
精确回归应该靠截图对比工具，而不是把像素阈值写死在业务代码里。
